# VLMD Subtask 1 — Annotation System

The software that runs the cognitive mechanism annotation study: a deployed web
application that serves 1,621 arguments to annotators, records their judgements
durably, and produces the validated export and agreement report the analysis
depends on.

The study interface is [Potato](https://potatoannotator.com/) 2.9.3 on Python
3.9, with this repository supplying the task definition, a set of runtime
patches, the corpus build, the export and validation pipeline, the agreement
report, the administrative console and the storage architecture. The task
itself is documented in `DESIGN.md` and `guidelines.md`.

## What the system is made of

The deployment is a single Railway service running three processes in one
container, alongside a Postgres service.

```
                         study-production-90a4        study-production-8fd9
                                   │                            │
   ┌───────────────────────────────┼────────────────────────────┼──────────┐
   │  container                    ▼                            ▼          │
   │                      serve.py (:$PORT)          annotation_backend.py │
   │                      the study server            the console (:8766)  │
   │                             │                            │            │
   │                             ▼                            │            │
   │                    annotation_output/  ◄──────────────────┘            │
   │                    (Railway volume)                                    │
   │                             │                                          │
   │                             ▼                                          │
   │                      mirror_loop.py  ── every 15 min ──►  Postgres     │
   └────────────────────────────────────────────────────────────────────────┘
```

`scripts/start.sh` is the container entry point. It writes the admin key file,
starts the console and the mirror in the background, and execs the study server
in the foreground so that it is PID 1 and receives shutdown signals directly.
The mirror and the console are separate processes by design: neither can slow
down or crash an annotator's save.

The two public domains point at different ports of the same service. Port
`$PORT` serves the study; port 8766 serves the console, which is gated behind
the admin key.

## How the interface is produced

The annotation form is generated by Potato from the schemes in `config.yaml`
and cached in `layouts/`, which is regenerated whenever the configuration hash
changes. Conditional questions are driven by `display_logic` rather than an
explicit layout, which is why adding a `layout:` block silently breaks the form.

Four behaviours the study requires are not available in Potato's configuration
and are applied at runtime by `scripts/serve.py`, which wraps the relevant
functions before the server starts rather than forking the package:

The guidelines are rendered into a banner above every argument, read from
`guidelines.md` at boot. This keeps the mechanism definitions in one file rather
than duplicated between the interface and the annotator documentation. The boot
sequence warns if the six mechanism names in that file have drifted from the six
labels in `config.yaml`.

Completion is redefined so that an argument can be left part-answered. Potato
treats any answer as completion; the study needs a distinction between a draft
and finished work, so the completeness predicate, the progress counter and the
navigation badge are all replaced with versions that agree on a single
definition. `static/study.js` is inlined into every page and splits Potato's
single Next button into Save draft and Submit, validating Submit against the
same requirement list the server derives from the schemes, so the button and the
badge cannot disagree.

Navigation is changed from next-unannotated to next-adjacent, so that every
argument is one press away from its neighbour and a finished argument can be
revisited.

Sign-in is replaced by `scripts/accounts.py`, described below.

Each patch is applied by wrapping an existing entry point, so Potato continues
to be upgradeable and the reasons are recorded next to the code rather than
buried in a diff.

## Sign-in and access control

Annotators sign in with a NetID and no password. A NetID the study has not seen
creates an account on first use; the same NetID returns the annotator to their
own work. This is `require_password: false` with open enrolment, and it is a
deliberate trade for a small internal study with a known roster: the alternative
was a password store, a reset flow and a mailbox to operate it.

**The NetID is therefore the whole credential.** Anyone who has the study URL
and knows a NetID can annotate as that person. The study URL should be treated
as the access control boundary, and the console's completion table is the record
of who annotated what. Restoring passwords is a single configuration change:
`require_password: true` restores the password field, the registration tab and
the reset flow that Potato provides.

Three things are enforced regardless:

A NetID is validated before it becomes an account. It is used verbatim as a
directory name, and Potato applies no constraint to it, so without a rule on its
shape an input such as `../../something` would select a directory outside the
output tree. The accepted form is 3 to 64 characters of letters, digits and
`. _ + - @`, which also admits the email addresses used by non-UTD annotators.

A NetID is lower-cased on sign-in. Without normalisation, two capitalisations of
one NetID are two annotators with two directories and one person's work divided
between them, and with no password there is nothing else that would detect it.

`/register` and `/forgot-password` are closed and redirect to the sign-in page.
Neither is linked from a passwordless interface, but both remain routed by
Potato, and its forgot-password handler issues a valid reset token for any
username submitted to it and renders the link in the response. In a study with
no passwords that endpoint has no function and considerable reach, so it is
disabled rather than left unreferenced.

**Sessions.** The session is a Flask signed cookie carrying the NetID, marked
`HttpOnly`, valid for 14 days, and signed with `POTATO_SECRET_KEY` from the
environment. A stable key is what allows a redeploy without logging every
annotator out; without one, Flask generates a key per process and every session
is invalidated on each deploy. The cookie is signed rather than encrypted, so a
client can read the NetID in it but cannot alter it. Railway terminates TLS on
both domains, so the cookie is only ever transmitted over HTTPS in practice,
although the `Secure` and `SameSite` attributes are not set explicitly.

**Administrative access.** Two surfaces require the admin key. Potato's own
dashboard at `/admin` prompts for it in the browser and its JSON endpoints
require it as an `X-API-Key` header. The console on port 8766 is bound off
loopback and rejects every request that arrives without the key, failing closed
if the key file is absent. The key is supplied as `POTATO_ADMIN_API_KEY` and
written to `admin_api_key.txt` by the container entry point, because the console
reads the file rather than the environment.

The console accepts the key as a query parameter, since a browser will not
attach a header to a navigation. One consequence worth recording: the key
appears in the platform's HTTP logs and in browser history. Rotating it means
changing the environment variable and redeploying.

## How annotations are stored

**The write path.** Each annotator has one file, `annotation_output/<netid>/
user_state.json`, holding their assigned ordering, their position in it, and
every answer, justification, note, flag and timing record they have entered.
Every save rewrites that file in full through a temporary file, an `fsync` and
an atomic rename, so an interrupted write leaves either the previous version or
the new one and never a partial record. One file per annotator means concurrent
saves by different people cannot interfere with one another.

These files are the source of truth. The export, the agreement report and the
console all read them directly, and no other component is authoritative.

There is no account database. A passwordless sign-in stores no credential, so
an annotator's directory is the only record that they exist; `user_config.json`
remains on the volume but holds nothing the study depends on.

**Durability.** `annotation_output/` is a Railway volume: persistent storage
attached to the container rather than part of its filesystem image. A deploy
replaces the container and leaves the volume in place, which is the only reason
annotations survive a deploy at all. The volume is mounted at that path
specifically because the export, the console and the mirror all resolve it
relative to the repository root.

This is also why the service must run exactly one replica. Potato holds each
annotator's state in the memory of a single process; a second replica would
maintain a divergent copy of the same state and the two would overwrite each
other on the shared volume.

**The mirror.** `scripts/mirror_to_postgres.py` copies annotations into
Postgres every fifteen minutes, driven by `mirror_loop.py` as its own process on
its own clock. It is derived storage and is deliberately outside the save path:
if Postgres is unreachable, slow or broken, annotation continues unaffected and
the failure is recorded rather than propagated. The record definition is
imported from the export module, so the mirror, the CSV and the agreement report
cannot develop separate ideas of what an annotation is.

Three tables:

| Table | Contents |
|---|---|
| `annotation` | The current state of each annotation, one row per annotator and argument |
| `annotation_history` | Append-only. Every version the mirror has observed, never updated or deleted |
| `mirror_run` | One row per pass: rows seen, rows changed, success, and the error if any |

`annotation_history` is the substantive reason for the mirror. Volume backups
provide daily snapshots; the history table provides every intermediate state, so
an overwrite or an annotator clearing their own work is recoverable between
snapshots. `mirror_run` exists because a mirror that has silently stopped and a
mirror with nothing to copy are otherwise indistinguishable.

**What the mirror does not hold.** It stores annotation records, not annotator
state files. The assigned instance ordering, the annotator's position within it
and the behavioural data are not in Postgres. Postgres is therefore sufficient
to recover the research data and not sufficient to reconstruct a running study;
that is what volume backups are for, and they should be enabled on both the
study volume and the Postgres service. Because a volume's backups are destroyed
with the volume, a periodic copy held outside Railway is worth keeping.

## Export and validation

```bash
python scripts/export_annotations.py --strict
```

Writes `annotations.csv`, `annotations.jsonl` and `validation_report.json` into
`annotation_output/export/`, and exits non-zero if any record violates a study
constraint. Potato's own automatic exports are retained as a safety net but are
not the deliverable: they produce one sparse column per scheme and label, carry
no item fields and no timestamps.

The validator enforces the constraints the interface cannot: that a mechanism is
recorded on an argument if and only if it failed the Sensible Test, that no
mechanism is both primary and secondary, that every recorded mechanism carries a
substantive justification and no justification is orphaned from its mechanism,
and that no part-answered argument reaches the export. `--self-test` runs the
validator against synthetic violations to confirm each check still fires.

## Agreement

`scripts/agreement.py` computes Krippendorff's alpha, Fleiss' and Cohen's kappa,
alpha-MASI for the multi-label question and observed agreement, per question and
per annotator pair, with confusion tables for the mechanism questions. Every
coefficient is reported with the number of arguments it was computed on, and an
undefined coefficient states why rather than rendering as blank.

Potato's own `/admin/iaa` endpoint returns null for this study. It scores only
items with a per-item annotator cap of two or more, and this study sets no cap
because work is distributed by argument range rather than by assignment. The
console's report is computed over the overlap actually present on disk.

## The console

`scripts/annotation_backend.py` provides what Potato's dashboard does not:
extraction, side-by-side comparison, agreement, and the flag queue. It reads
`annotation_output/` directly, writes nothing, makes no assignments and sends
nothing to the study server, so it can be run against a downloaded copy with the
study stopped. `scripts/pull_annotations.sh` fetches that copy from the volume.

Four tabs: downloads and per-annotator completion; every annotation grouped
under its argument, with filters and a CSV of whatever is on screen; the
agreement report; and the arguments flagged for discussion.

## Operational constraints

Some of these fail silently and are recorded here for that reason.

- One replica. Not a tuning parameter; see above.
- The volume must be mounted at `annotation_output/`.
- Do not add a `layout:` block to `config.yaml`. It disables `display_logic`
  and places every conditional question permanently on screen, with no error.
- Do not rename an annotation scheme after annotation has begun. Existing
  answers become invisible to the admin view, the agreement report and the
  export, with no error.
- A corpus rebuild does not reorder annotators already working. Potato assigns
  the ordering once and stores it in the annotator's state file.
  `scripts/resync_order.py` re-aligns them to a rebuilt corpus while keeping
  each on the argument they were working on, and must be run with the server
  stopped.
- Start the server through `scripts/serve.py`. `potato start config.yaml`
  produces a study with no guidelines banner and no drafts.

## Verification

```bash
python scripts/walk_study.py   --url <url>    # every branch, drafts, refusals
python scripts/capture_ui.py   --url <url>    # full-page screenshots
python scripts/export_annotations.py --self-test
python scripts/verify_deploy.py --url <url> --admin-key <key> --annotate
python scripts/verify_deploy.py --url <url> --admin-key <key> --check
```

`walk_study.py` drives the interface end to end and verifies what reached disk.
`verify_deploy.py` is the volume and session test: `--annotate` records an
annotation, and after a redeploy `--check` confirms through the admin API that a
process started since then still has it, and that the saved session cookie still
authenticates. Both leave a throwaway annotator directory to delete afterwards.

## Repository layout

```
config.yaml              Task definition: schemes, display logic, sign-in, keys
guidelines.md            Annotator guidelines, rendered into the interface
args_0911.json           Source corpus
data/                    Built corpus: instances.json, manifest.json
static/                  Interface stylesheet and client script
layouts/                 Generated form cache; regenerated on a config change
scripts/                 Everything below
annotation_output/       The annotation store; a volume in the deployment
```

| Script | Purpose |
|---|---|
| `build_instances.py` | Builds the corpus and manifest from the source file |
| `serve.py` | Starts the study server and applies the runtime patches |
| `accounts.py` | NetID validation and sign-in; closes the password endpoints |
| `export_annotations.py` | Downstream CSV and JSONL, and the validator |
| `agreement.py` | Inter-annotator agreement coefficients and confusion tables |
| `annotation_backend.py` | The administrative console |
| `mirror_to_postgres.py` | One mirroring pass; also `--verify` and `--dry-run` |
| `mirror_loop.py` | Runs the mirror on a fifteen-minute clock |
| `start.sh` | Container entry point; starts all three processes |
| `pull_annotations.sh` | Copies the deployed annotations to a local working copy |
| `walk_study.py` | End-to-end test of every branch of the interface |
| `capture_ui.py` | Screenshots of each interface state |
| `verify_deploy.py` | Volume and session verification against a deployment |
| `resync_order.py` | Re-aligns existing annotators after a corpus rebuild |
